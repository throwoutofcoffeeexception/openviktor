# Viktor A2A owner endpoint (candidate, 08.10.2026)

This candidate adds a `/a2a` JSON-RPC `message/send` and `tasks/get` adapter to the existing guest agent runtime. It is disabled unless all of `VIKTOR_TWIN_BINDING_FILE`, `VIKTOR_A2A_AUDIENCE`, `VIKTOR_A2A_TENANT`, and `VIKTOR_A2A_PUBLIC_KEY_FILE` are set. The binding file contains only `{"workspaceId":"...","principalId":"tg-..."}` (mode 0400/0600), without an expiring owner grant or token. The service credential is Twin's Ed25519 signing key; the verifier is the corresponding public PEM, owned by root or the bot process, and not writable by group/others. The audience must be the exact HTTPS AgentCard URL. The tenant is the Alpha caller's `tvin.owner_scope.tenant` (for example `alpha`), while the guest workspace ID is independently bound by the trusted guest binding; they must not be assumed equal.
The same optional guest gateway serves a public read-only `/.well-known/agent-card.json` with its exact A2A URL and HTTP bearer JWT security scheme. It is not reachable when the A2A configuration is disabled; publish the card only behind a scoped ingress after a live positive/negative owner task.

An authenticated request needs a signed EdDSA JWT (`iss=twin`, `scope=twin:agent`, `sub=owner:tg:<positive numeric id>`, `aud=<exact AgentCard URL>`, integer `iat`, `exp<=iat+300`, `jti`) and the permanent guest binding must bind the same `tg-<id>` principal to the configured workspace. The short lifetime protects the bearer against replay; it is generated per task by Twin, not an owner-approval window. The client must send `tvin.owner_scope={tenant,ownerId}` in message metadata. The adapter reserves `(workspace,principal,requestId)` durably and persists the task-text digest before running the real agent with read-only `read_learnings`. A duplicate request with different text fails 409. `tasks/get` reads only the matching owner-scoped durable reservation and receipt. A timeout leaves the task working for reconciliation, never launches another model run. A completed Task artifact is agent text, **not** proof of delivery to the owner or accuracy of business claims.
JSON-RPC request `id` may be a string or an integer and is distinct from the durable message `messageId`. RPC failures after parsing an ID return `{jsonrpc,id,error:{code,message}}`. A reservation of unknown outcome remains `working` until an actual terminal run receipt can be established; age alone cannot prove failure.

The guest's legacy `/v1/agent/run` and existing bearer grant remain unchanged. Installing a verifier key, configuring HTTPS proxy/guest route, enabling the verified card, and a sanctioned owner-channel Task/readback are separate gates, not proven by these local tests. Never expose the bot gateway directly to the internet, invent a grant, or mark the card verified based on this candidate alone.
